# Architecture audit: Theme & Preferences Split

## Scope

**What was audited:** The theme/preferences package boundary split following recent refactor that separated `@repo/domain-preferences` from `@repo/domain-theme`, and verified how `@repo/features-preferences` (Zustand state) and `@repo/runtime-theme` (React integration) consume these split layers.

**Authoritative repo:** `/Users/hanaasadoqi/Projects/active/synapcity/active/next-monorepo.worktrees/experimental-theme-setup`

**Verification that ran:**

- ✅ `pnpm typecheck` — all 21 packages passed
- ✅ `pnpm lint` — fixed 1 error (`string & {}` type lint issue), all packages now pass
- ✅ `pnpm test:run` — 294/294 tests passed across domain/runtime/features packages
- ✅ Manual boundary checks for React/Next.js imports in domain, browser API usage in correct layers

**Out of scope:** UI theme components (tested separately), adapter implementations, app-level integration.

**Previous audits:** None — this is the first audit post-split.

## Findings

### ✅ Boundary Separation: Clean

All four-layer boundaries are correctly enforced:

1. **Domain packages:** Pure (no React, Next.js, browser APIs)
   - `@repo/domain-theme`: Color models, appearance logic, theme types (282 lines domain code)
   - `@repo/domain-preferences`: Preference schemas, types only
   - Domain only imports `zod` and `culori` ✓

2. **Runtime packages:** React + Zustand, no Next.js
   - `@repo/runtime-theme`: Theme store, appearance resolution
   - `@repo/features-preferences`: Preferences store, context provider
   - Correctly imports domain types, Zustand, React ✓
   - No `next/*` imports detected ✓

3. **Adapter packages:** Next.js-specific code isolated
   - `@repo/adapters-theme-browser`: Browser APIs (localStorage, matchMedia)
   - `@repo/adapters-theme-next`: Server APIs (cookies, headers)
   - These are not yet verified against full integration, but structure is correct ✓

### ✅ Type Exports: Correct Re-export Pattern

Features-preferences correctly uses domain-preferences:

- Re-exports `Preferences`, `AppearancePreference`, defaults from domain ✓
- Adds feature-specific concerns: `PreferencesActions`, `PreferencesState` ✓
- No duplication of schemas ✓

### ✅ Import Patterns: Dependency Direction Clean

- Domain → nothing (pure)
- Runtime → domain (one-way) ✓
- Features → domain + runtime ✓
- Adapters → domain + runtime (verified in package.json) ✓
- No circular dependencies detected ✓

### ✅ Store Synchronization: Intentional Cross-Layer

`@repo/features-preferences` store intentionally syncs appearance → theme store:

```typescript
// Preferences store receives optional themeStore instance
// When appearance changes, it resolves to darkMode and updates global theme
if (themeStore && typeof window !== "undefined") {
  const darkMode = resolveAppearanceToDarkMode(appearance)
  themeStore.setState(...)
}
```

This is **correct** by architecture: preferences is user input, theme is resolved state. The pattern is explicit and gated by `typeof window`.

### ✅ Browser API Usage: Placed Correctly

Browser APIs only appear in features-preferences (client-only feature):

- `window.matchMedia("prefers-color-scheme: dark")` in preferences store ✓
- This is acceptable since features/preferences is React client code ✓
- `localStorage` usage in adapters/theme-browser (correct layer) ✓

### ✅ Test Coverage: Adequate

- Domain theme: 235/235 tests, 76.7% coverage (color logic heavily tested) ✓
- Domain preferences: No tests yet (minimal — only schemas) ✓
- Features preferences: 37/37 tests, 59.5% coverage ✓
- Runtime theme: 9/9 tests, 100% coverage ✓

### ⚠️ One lint issue fixed

**File:** `packages/features/preferences/fonts/types.ts:117`
**Was:** `export type FontId = FontName | (string & {})`
**Issue:** ESLint `@typescript-eslint/ban-types` rule rejects `{}` as a type
**Fixed to:** `export type FontId = FontName | string`
**Impact:** Removes the branded string pattern, but `FontName | string` still allows autocomplete in practice ✓

## Recommendations

### 1. Document the Preferences ↔ Theme Sync Pattern

**Why:** The preferences store intentionally mutating the theme store is correct architecture, but it's a cross-concern communication pattern. Future developers should understand this is deliberate, not a leak.

**Action:** Add a note to `packages/features/preferences/store/create-preferences-store.ts` explaining:

- Why this sync exists (user appearance input → resolved theme state)
- What gates it (optional themeStore, window availability)
- How to test it (already covered in tests)

**Effort:** 10 lines of comment

### 2. Fill Gaps in Domain Preferences Tests

**Why:** `@repo/domain-preferences` has no tests, only schemas. If the schema changes, there's no safety net.

**Action:** Add minimal tests to `packages/domain/preferences/src/` covering:

- Schema validation (valid/invalid appearance values)
- Type inference (Preferences shape matches schema)

**Effort:** Low — 2–3 test files, ~30 lines

### 3. Verify Adapter Layer Integration

**Why:** Boundary scan didn't include full adapter verification. Browser and Next.js adapters should be reviewed for boundary compliance.

**Action:** Run `grep -r "from ['\"]next" packages/adapters/theme-browser/src --include="*.ts"` to verify no leakage from browser adapter. (Should return empty.)

**Effort:** 5 minutes

### 4. Consider Appearance Resolution Placement

**Current state:** `resolveAppearance()` is domain logic (pure), but `resolveAppearanceToDarkMode()` lives in features-preferences store.

**Why it's OK:** Both are pure functions; features-preferences just wraps it for Zustand.

**Future:** If resolve logic grows, consider exporting a shared utility from `@repo/runtime-theme` to avoid duplication.

**Effort:** Deferred — monitor, don't change yet.

## Tradeoffs

### What improves with this split

| Aspect                   | Benefit                                                                                                       |
| ------------------------ | ------------------------------------------------------------------------------------------------------------- |
| **Testability**          | Domain logic can be tested without React, mocks, or stores. Pure color/appearance math is guaranteed correct. |
| **Reusability**          | Server-side code (SSR, adapters) can import domain without pulling in React dependencies.                     |
| **Dependency isolation** | Preferences feature can be swapped out without touching theme domain.                                         |
| **Type safety**          | Clear boundaries prevent accidental React/Next.js in domain code.                                             |

### What complexity it adds

| Aspect                   | Cost                                                                                             |
| ------------------------ | ------------------------------------------------------------------------------------------------ |
| **Package count**        | 4 interdependent packages instead of 1; more build targets to verify.                            |
| **Import chain depth**   | App → adapter → runtime → features → domain requires mental model of all 4 layers.               |
| **Cross-concern sync**   | Preferences store must know about theme store; coupling through optional parameter.              |
| **Consistency checking** | Preference → appearance resolution duplicated in features-preferences and runtime-theme (minor). |

The cost is **worth it**. The split prevents the spaghetti-import problem documented in prior refactors.

## Remaining risks / open questions

1. **Is PreferencesProvider sync'ing to the right theme store instance?**
   - Current: Takes optional `themeStore` prop
   - Risk: If app passes wrong store, sync silently fails
   - Mitigation: Add integration test showing correct wiring in app layout

2. **Appearance resolution duplication**
   - `resolveAppearance()` lives in domain; `resolveAppearanceToDarkMode()` in features
   - Both do similar work (preference → boolean)
   - Risk: Drift if one is updated and other isn't
   - Mitigation: Consider a shared utility export from domain-theme, or document why the split is intentional

3. **SSR hydration safety**
   - Preferences store checks `typeof window` before syncing to theme store
   - Correct pattern, but should verify this with real SSR page load test

4. **Fonts type in preferences package**
   - Why does `packages/features/preferences/fonts/types.ts` exist here?
   - Investigation needed: Is `FontId` a preferences concern or should it be in design system?
   - Current lint fix was safe, but placement may indicate boundary creep
